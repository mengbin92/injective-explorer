# 性能瓶颈分析：本地1000 TPS vs 服务器10 TPS

## 问题描述

- **本地测试**：TPS 约 1000
- **服务器测试**：TPS 约 10
- **服务器带宽**：5M

性能差异达到 **100倍**，这是一个严重的性能问题。

## 根本原因分析

### 1. 响应体未读取（最关键问题）⭐

**问题位置**：`cmd/loadtest/main.go` 的 `makeRequest` 函数

**当前代码问题**：
```go
resp, err := client.Get(u.String())
// ...
if resp != nil {
    defer resp.Body.Close()  // ❌ 只关闭，未读取
}
```

**问题影响**：
1. **连接无法复用**：HTTP/1.1 要求必须读取完响应体才能复用连接
2. **每个请求都建立新连接**：导致大量 TCP 握手开销（3次握手 + TLS握手）
3. **网络延迟增加**：每次连接建立需要额外时间
4. **带宽利用率低**：大量带宽浪费在连接建立上

**本地 vs 服务器差异**：
- **本地**：localhost 连接建立极快（<1ms），即使不读取响应体，连接建立开销也很小
- **服务器**：网络延迟较高（可能 10-100ms），连接建立开销显著，导致性能急剧下降

### 2. 网络带宽限制（5M）

**带宽计算**：
- 5Mbps = 5 × 1024 × 1024 / 8 = 655,360 字节/秒 ≈ 640 KB/s

**假设场景**：
- 每个响应平均 10KB
- 理论最大请求数：640 KB/s ÷ 10 KB = 64 请求/秒
- 但实际由于连接建立开销，性能会更低

**如果响应更大**：
- 20KB 响应：32 请求/秒
- 50KB 响应：12.8 请求/秒
- 100KB 响应：6.4 请求/秒

### 3. 连接池配置不足

**当前配置**：
```go
MaxIdleConns:        100
MaxIdleConnsPerHost: 20
```

**问题**：
- 如果连接无法复用（由于未读取响应体），连接池配置再大也没用
- 每个请求都需要新连接，连接池很快被耗尽

### 4. 网络延迟影响

**本地测试**：
- 延迟：<1ms
- 连接建立：几乎瞬时
- 即使不读取响应体，开销也很小

**服务器测试**：
- 延迟：可能 10-100ms（取决于网络质量）
- 连接建立：需要 3 次握手 + 可能 TLS 握手
- 如果每个请求都建立新连接，延迟会累积

## 性能差异计算

### 本地场景（假设）
- 连接建立时间：0.5ms
- 请求处理时间：1ms
- 响应传输时间：0.5ms（假设响应很小）
- **总时间**：2ms
- **理论 TPS**：1000 TPS（如果连接可复用）

### 服务器场景（当前问题）
- 连接建立时间：50ms（网络延迟 + TCP握手）
- 请求处理时间：1ms
- 响应传输时间：10ms（假设响应 10KB，5M带宽）
- **总时间**：61ms
- **理论 TPS**：16 TPS

**但实际更低**，因为：
- 响应体未读取，连接无法复用
- 每个请求都需要新连接
- 带宽被浪费在连接建立上

## 解决方案

### 1. 修复响应体读取问题（必须）⭐

**修改 `makeRequest` 函数**：
```go
// 读取并丢弃响应体，确保连接可以复用
if resp != nil {
    defer resp.Body.Close()
    // 读取响应体（即使丢弃）以确保连接可以复用
    io.Copy(io.Discard, resp.Body)
}
```

**效果**：
- 连接可以复用
- 减少 TCP 握手开销
- 提升性能 10-100 倍

### 2. 优化连接池配置

```go
Transport: &http.Transport{
    MaxIdleConns:        200,        // 增加总连接数
    MaxIdleConnsPerHost: 100,        // 增加每个host的连接数
    IdleConnTimeout:     90 * time.Second,
    DisableCompression:  false,      // 启用压缩
    TLSHandshakeTimeout: 10 * time.Second,
    // 启用 HTTP/2（如果服务器支持）
    ForceAttemptHTTP2:   true,
}
```

### 3. 启用响应压缩

**服务器端**：已启用（`DisableCompression: false`）

**效果**：
- 减少响应大小
- 提升带宽利用率
- 降低传输时间

### 4. 分析响应大小

**建议**：
- 监控实际响应大小
- 优化大数据接口（分页、字段过滤）
- 考虑使用流式传输

### 5. 考虑升级带宽

**当前**：5M
**建议**：至少 20-50M（取决于实际响应大小和预期 TPS）

## 预期性能提升

### 修复响应体读取后

**假设**：
- 连接可复用
- 平均响应 10KB
- 网络延迟 50ms（首次连接）
- 后续请求延迟 1ms（复用连接）

**计算**：
- 首次请求：50ms（连接建立）+ 1ms（处理）+ 10ms（传输）= 61ms
- 后续请求：1ms（处理）+ 10ms（传输）= 11ms
- 平均：假设 90% 连接复用，平均延迟 = 0.1 × 61 + 0.9 × 11 = 16ms
- **理论 TPS**：1000ms / 16ms = 62.5 TPS

**带宽限制**：
- 5M 带宽 = 640 KB/s
- 10KB 响应 = 64 请求/秒（理论最大）
- **实际 TPS**：约 50-60 TPS（考虑开销）

### 如果响应更小（5KB）

- 理论最大：128 请求/秒
- 实际 TPS：约 100-120 TPS

### 如果响应更大（20KB）

- 理论最大：32 请求/秒
- 实际 TPS：约 25-30 TPS

## 总结

**主要问题**：
1. ✅ **响应体未读取**（最关键）- 导致连接无法复用
2. ⚠️ **网络带宽限制**（5M）- 限制最大吞吐量
3. ⚠️ **连接池配置** - 需要优化但非主要问题

**修复优先级**：
1. **立即修复**：响应体读取问题
2. **短期优化**：连接池配置、响应压缩
3. **长期考虑**：升级带宽、优化响应大小

**预期效果**：
- 修复响应体读取后：TPS 从 10 提升到 50-100（5-10倍）
- 如果响应较小：TPS 可能达到 100-200
- 如果响应较大：TPS 可能只有 20-50（受带宽限制）
