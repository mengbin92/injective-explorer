# block_signers 表必要性分析

## 当前使用情况

### 1. 数据写入
- `SaveBlockSigners` 函数：每个块同步时保存签名者信息
- 同时更新聚合统计表（方案3）

### 2. 数据读取
- `GetValidatorBlockStats` API：从 `block_signers` 表统计 proposed/signed
- `validator_stats.go`：作为回退方案（如果聚合统计表不可用）

### 3. 数据量
- 100个验证者，1000个块，平均50个签名/块 = 50,000条记录
- 相比聚合统计表的100条记录，数据量大500倍

## 是否可以移除？

### 可以移除的理由

1. **主要需求已满足**：
   - 统计总数（proposed/signed/missed）已由聚合统计表提供
   - 查询性能最优：直接查询聚合统计，无需 COUNT

2. **数据量巨大**：
   - 50,000条 vs 100条（减少99.8%）
   - 随着块数增长，数据量会持续增长

3. **没有详细查询需求**：
   - 当前没有API需要查询某个验证者在某个具体块的参与情况
   - 没有需要历史详细数据的场景

### 需要保留的理由

1. **回退方案**：
   - 如果聚合统计表有问题，可以从 `block_signers` 表重新计算
   - 提供数据验证和修复能力

2. **未来扩展**：
   - 可能需要查询某个验证者在某个块的参与情况
   - 可能需要时间段内的详细统计

3. **调试和审计**：
   - 可以追溯具体哪个块发生了什么
   - 便于问题排查和数据验证

## 推荐方案

### 方案A：完全移除（推荐，如果不需要详细查询）

**优点**：
- 数据量最小
- 代码更简单
- 性能最优

**缺点**：
- 失去详细查询能力
- 没有回退方案

**实施步骤**：
1. 移除 `block_signers` 表的创建
2. 移除 `SaveBlockSigners` 函数中的保存逻辑
3. 修改 `GetValidatorBlockStats` 和 `validator_stats.go`，只使用聚合统计表
4. 删除 `block_signer.go` 文件

### 方案B：保留但定期清理（折中方案）

**优点**：
- 保留最近N个块的详细数据（用于调试）
- 数据量可控（只保留最近数据）
- 有回退方案

**缺点**：
- 仍然需要存储部分数据
- 需要定期清理逻辑

**实施步骤**：
1. 保留 `block_signers` 表
2. 添加定期清理逻辑（如只保留最近10,000个块）
3. 修改代码，优先使用聚合统计表

### 方案C：完全保留（如果未来需要详细查询）

**优点**：
- 保留所有详细数据
- 支持未来扩展

**缺点**：
- 数据量最大
- 存储成本高

## 实施结果

**已采用方案A（完全移除）**：

1. ✅ 移除了 `block_signers` 表的创建（`init_database.sql`）
2. ✅ 修改了 `SaveBlockSigners` 函数，不再保存到 `block_signers` 表，只更新聚合统计表
3. ✅ 修改了 `GetValidatorBlockStats` API，使用聚合统计表查询
4. ✅ 修改了 `validator_stats.go`，使用聚合统计表
5. ✅ 简化了 `block_signer.go`，移除了 `BlockSigner` 模型，只保留内部使用的 `SignerInfo` 结构

**优势**：
- 数据量减少99.8%（100条记录 vs 50,000条记录）
- 查询性能最优（直接查询聚合统计，无需 COUNT）
- 代码更简单（无需维护详细记录）

**注意事项**：
- 如果未来需要查询某个验证者在某个具体块的参与情况，需要重新添加 `block_signers` 表
- 如果需要历史详细数据，可以考虑方案B（定期清理）
